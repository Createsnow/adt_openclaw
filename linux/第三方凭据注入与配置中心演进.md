# 第三方凭据注入与配置中心演进

> 本文档由仓库根目录原文档**重组**而来：只调整章节归属与交叉引用，**不改变**部署步骤、命令、YAML、错误码或禁止事项。阅读顺序见 [README.md](README.md)。

适用对象：已完成工位 WSL2 或 Linux 服务器安装手册中 **Docker secrets + entrypoint + `${VAR}`** 部署的工程师；计划将凭据与第三方请求参数收口到 **Nacos** 或企业统一配置平台。

本文档说明：**当前方案**、**凭据边界**、**未来目标架构**、**迁移路径**与**约束**。操作步骤以安装手册第 6 节为准：**工位** [WSL2 手册](OpenClaw%20Gateway%20WSL2-Docker%20安装手册.md) **6.0–6.5**；**Linux 服务器**该手册 **第 6 节（6.1 变量表）**，entrypoint / compose 在第 7–8 节，模型写入在第 12 节。

## 0. 凭据与安全边界

代码、配置结构和业务规则可以进本仓库；生产凭据、员工工单和身份原值不能随代码提交。工程师应在自己的授权环境重新申请，或由管理员现场写入 `~/xa/secrets/`。

| 凭据 | 接手动作 |
| --- | --- |
| 企微 BotId / BotSecret | 不复制；新环境由企微管理员重新配置 |
| 企业 CorpID / CorpSecret（身份转换） | 不复制；仅身份服务所需账号重新授权 |
| Gateway Token | 不复制；目标环境重新生成 |
| 模型 API Key | 不复制；百炼控制台重新申请 |
| OA AppSecret / API 用户 ID | 不复制；由 OA 管理员指定。旧值若曾暴露须轮换 |

**绝对禁止进入本仓库、聊天或截图：** CorpSecret、Bot Secret、OA AppSecret、模型 API Key、Gateway / OAuth Token、私钥、原始 SenderId / 明文 userid / 手机号 / 邮箱、真实工单正文和附件。

`openclaw.json` 只写 `${VAR}`。日志不得记录 Header、token、密文、附件 base64 和身份原值。测试数据用脱敏样例，不复制生产工单。

## 1. 设计目标

| 目标 | 说明 |
| --- | --- |
| 隔离 | 第三方凭据、认证、endpoint、模型 ID 等不由 OpenClaw 手填或落盘明文 |
| 统一 | 未来由配置平台（如 Nacos）作为「真值源」 |
| 可演进 | 从当前 Docker 注入平滑迁移，**不重写** `openclaw.json` 业务结构 |
| 契约稳定 | 环境变量名（工位手册 **6.0** / Linux 服务器手册 **6.1**，两边相同）长期不变，只换「谁赋值」 |

OpenClaw 侧始终保留：

- `openclaw.json`：**结构骨架** + `${VAR}` 占位符（gateway、channels、models、agents、plugins、tools…）
- `~/xa/workspace/`：业务规则（非第三方参数）

## 2. 当前方案（已验证基线）

```text
~/xa/secrets/*.txt（宿主机，chmod 600）
        ↓  Docker Compose secrets → /run/secrets/
~/xa/entrypoint.sh（export 为大写环境变量）
        ↓
openclaw.json（仅 ${OPENCLAW_GATEWAY_TOKEN}、${XA_DOMESTIC_BASE_URL} 等占位符）
        ↓
OpenClaw Gateway
```

### 2.1 两阶段顺序（不可颠倒）

| 阶段 | 检查清单步 | secret 数量 | 内容 |
| --- | --- | --- | --- |
| **A：初装** | 工位 6–7 | 3（工位分阶段） | Gateway Token、企微 BotId/BotSecret |
| **B：模型** | 工位 9 | +5 | 模型 Key、baseUrl、model id、model ref、api 协议 |

变量名与 secret 文件名契约**只在安装手册写全**：工位 **6.0**，Linux 服务器 **6.1**（两边变量名相同）。本节只记注入方式，不重复变量表。

### 2.2 参数分类

| 类别 | 示例 | 当前注入方式 | 是否进 json 明文 |
| --- | --- | --- | --- |
| 高敏凭据 | Gateway Token、BotSecret、API Key | secret → `${VAR}` | 否 |
| Endpoint | 模型 `baseUrl` | secret → `${XA_DOMESTIC_BASE_URL}` | 否 |
| 请求参数 | model id、api 协议、model ref | secret → `${VAR}` | 否 |
| Catalog 元数据 | contextWindow、maxTokens | json 固定值 | 可（非 secret） |
| 业务结构 | agent id、tools 白名单、bindings | json | 是（非第三方） |

### 2.3 当前方案优点与局限

| 优点 | 局限 |
| --- | --- |
| 与已验证 WSL2 部署完全一致 | 变更 secret 需 `compose down/up`（env 进程级） |
| 无外部依赖，离线可部署 | 宿主机 `secrets/` 仍为明文文件（靠权限保护） |
| OpenClaw 无改造 | 多实例各自维护一份 `~/xa/secrets/` |
| 运维模型简单 | 无集中审计 / 版本 / 灰度 |

## 3. 未来方案：配置中心（Nacos）思路

### 3.1 目标架构

```text
Nacos（或企业配置平台）
  ├─ 加密命名空间：API Key、BotSecret、Gateway Token
  └─ 普通配置项：baseUrl、model id、api 协议
        ↓
  【取数层】三选一或组合（见 3.2）
        ↓
  与当前相同：entrypoint export ${VAR}  和/或  写入 /run/secrets/
        ↓
  openclaw.json（契约不变，仍全是 ${VAR}）
        ↓
  OpenClaw Gateway
```

**核心原则：** OpenClaw 不直连 Nacos；由 **取数层** 把平台配置转成现有环境变量契约。

### 3.2 三种取数架构（推荐顺序）

#### 架构 A：Nacos → 同步为宿主机 secret 文件（推荐首选）

```text
Nacos
  ↓ 定时/发布触发 sync 脚本（宿主机或 CI）
~/xa/secrets/*.txt
  ↓ 现有 entrypoint（不改 OpenClaw）
容器
```

| 项 | 说明 |
| --- | --- |
| 改动量 | 小：新增 sync 脚本，entrypoint / json **不变** |
| 可用性 | Nacos 短暂不可用不影响**已运行**容器；下次 sync + restart 才更新 |
| Bootstrap | Nacos AK/SK 或 mTLS 身份仍要一处可信注入（如单独 bootstrap secret） |
| 适用 | 从当前方案**零风险过渡** |

#### 架构 B：entrypoint 启动时直拉 Nacos

```sh
#!/bin/sh
set -eu
/usr/local/bin/nacos-fetch.sh   # 调 Open API，export 或写 /run/secrets/
# … 与现 entrypoint 相同的 export …
exec node dist/index.js gateway --bind lan --port 18789
```

| 项 | 说明 |
| --- | --- |
| 改动量 | 中：entrypoint 变长，需处理超时/重试 |
| 可用性 | **强依赖** Nacos；拉取失败则 Gateway 不起 |
| 适用 | Nacos 与容器同 VPC、SLA 有保障的生产环境 |

#### 架构 C：OpenClaw 原生 `secrets.providers.exec` + Nacos 解析器

凭据类字段可用 [OpenClaw Secrets Management](https://docs.openclaw.ai/gateway/secrets) 的 `exec` Provider；解析器实现 stdin/stdout JSON 协议，内部调 Nacos。

| 项 | 说明 |
| --- | --- |
| 凭据 | 适合 API Key 等 SecretRef 支持字段 |
| baseUrl | 通常**不在** SecretRef 凭据面，仍建议 `${XA_DOMESTIC_BASE_URL}` + entrypoint |
| 注意 | xA Docker 路径已**删除** Windows DPAPI 的 `secrets.providers`；引入 Nacos exec 需单独验证，可与 A/B 并存 |
| 热更 | 支持 `openclaw secrets reload`（凭据类） |

### 3.3 Nacos 配置建议（dataId / group 示例）

按环境隔离（勿 prod/staging 共用）：

| Nacos key（逻辑名） | 映射环境变量 | 敏感度 |
| --- | --- | --- |
| `xa.gateway.token` | `OPENCLAW_GATEWAY_TOKEN` | 高 |
| `xa.wecom.bot_id` | `XA_IT_WECOM_BOT_ID` | 中 |
| `xa.wecom.bot_secret` | `XA_IT_WECOM_BOT_SECRET` | 高 |
| `xa.model.api_key` | `XA_DOMESTIC_API_KEY` | 高 |
| `xa.model.base_url` | `XA_DOMESTIC_BASE_URL` | 低 |
| `xa.model.model_id` | `XA_DOMESTIC_MODEL_ID` | 低 |
| `xa.model.model_ref` | `XA_DOMESTIC_MODEL_REF` | 低 |
| `xa.model.api` | `XA_DOMESTIC_API` | 低 |

**变量名必须与安装手册 6.0 一致**，sync 脚本只做「Nacos 值 → secret 文件一行」或「→ export」。

### 3.4 不宜放入配置中心的内容

| 内容 | 保留位置 | 原因 |
| --- | --- | --- |
| Agent 工具白名单、deny 列表 | `openclaw.json` | 业务安全策略，非第三方 |
| workspace 规则（AGENTS.md 等） | `~/xa/workspace/` | 业务逻辑 |
| 插件 load.paths | `openclaw.json` | 部署结构 |
| bindings 路由 | `openclaw.json` | 业务路由 |
| OA `active=true` | 插件配置 | 阶段门控，见 OA 桥接接入手册 |

## 4. 迁移路径（推荐分三步）

### 步骤 1：固化变量契约（当前，已完成）

- 安装手册变量表内变量名不再随意改名（工位 **6.0** / Linux **6.1**）。
- 所有第三方真值只在 `~/xa/secrets/` + entrypoint。
- `openclaw.json` 仅 `${VAR}`。

**完成标准：** 检查清单第 9 步通过；`openclaw secrets audit` 无 json 明文 Key/URL（若已装对应 CLI）。

### 步骤 2：引入 Nacos 同步（架构 A）

1. 在 Nacos 创建 namespace / dataId，录入与安装手册变量表对应的键值（工位 6.0 / Linux 6.1）。
2. 编写 `nacos-sync-xa.sh`（运行在 WSL 宿主机或 CI）：
   - 读 Nacos → 写入 `~/xa/secrets/*.txt`（一行、无换行）
   - `chmod 600`；可选校验 `model_ref` = `<providers 键名>/` + `model_id`（现网 / Linux 为 `bailian/`；工位手册示例为 `domestic/`）
3. 发布流程：sync → `cd ~/xa && docker compose down && docker compose up -d`
4. **暂不修改** entrypoint 与 openclaw.json。

**完成标准：** 人工只改 Nacos，不改 secret 文件内容；重启后 Gateway 行为与改前一致。

### 步骤 3：可选增强

| 增强 | 说明 |
| --- | --- |
| entrypoint 直拉（架构 B） | 去掉宿主机 secret 持久化；需处理 Nacos 高可用 |
| exec Provider（架构 C） | 仅迁凭据类；baseUrl 仍走 env |
| 多实例 | 每套 `~/xa-*` 独立 Nacos group；禁止共用 dataId |
| 审计 | Nacos 变更记录 + 容器重启工单联动 |

## 5. 迁移对照表

| 维度 | 当前（Docker secrets） | 未来（Nacos + 取数层） |
| --- | --- | --- |
| 真值存储 | `~/xa/secrets/*.txt` | Nacos（加密 + 普通配置） |
| 注入方式 | entrypoint export | **相同** export（推荐） |
| openclaw.json | `${VAR}` 占位符 | **不变** |
| 变更生效 | 改文件 + down/up | 改 Nacos + sync + down/up |
| 初装顺序 | 6A → 7 → 8 → 6B | **不变** |
| Bootstrap | 无 | Nacos 访问凭据需 Docker secret 或机器身份 |

## 6. 风险与约束

| 风险 | 缓解 |
| --- | --- |
| Nacos 宕机导致启动失败（架构 B） | 优先架构 A；entrypoint 内缓存上次成功 snapshot |
| env 不热更 | 配置变更后统一 `compose down/up` 或文档化 reload 流程 |
| Bootstrap 循环 | Nacos AK/SK 用独立 bootstrap secret，不写入 openclaw.json |
| 多环境串配置 | 严格 namespace / group；`~/xa-staging` 与 `~/xa` 隔离 |
| Agent 可读进程 env | 与当前 Docker 方案同级；高敏环境配合容器隔离 / 最小权限 |
| 误用 CLI 写明文 | **工位**手册 **8.3**：禁止 `config set` 写 baseUrl/Key。Linux 服务器同等约束见该手册第 21 节（不要用 CLI 写真文 BotSecret / Key） |

## 7. sync 脚本逻辑示例（架构 A，伪代码）

```bash
# nacos-sync-xa.sh — 示意，需按实际 Nacos SDK/API 实现
XA_SECRETS=~/xa/secrets
fetch_nacos() { local key=$1; /* 调 Nacos API */; }

printf '%s' "$(fetch_nacos xa.gateway.token)"       > "$XA_SECRETS/gateway_token.txt"
printf '%s' "$(fetch_nacos xa.wecom.bot_id)"        > "$XA_SECRETS/wecom_bot_id.txt"
printf '%s' "$(fetch_nacos xa.wecom.bot_secret)"    > "$XA_SECRETS/wecom_bot_secret.txt"
printf '%s' "$(fetch_nacos xa.model.api_key)"       > "$XA_SECRETS/model_api_key.txt"
printf '%s' "$(fetch_nacos xa.model.base_url)"      > "$XA_SECRETS/model_base_url.txt"
printf '%s' "$(fetch_nacos xa.model.model_id)"      > "$XA_SECRETS/model_id.txt"
printf '%s' "$(fetch_nacos xa.model.model_ref)"     > "$XA_SECRETS/model_ref.txt"
printf '%s' "$(fetch_nacos xa.model.api)"           > "$XA_SECRETS/model_api.txt"
chmod 600 "$XA_SECRETS"/*.txt
```

发布后由运维或 CI 执行 sync，再 `docker compose down && docker compose up -d`。

## 9. 一句话

**现在：** 第三方参数 → Docker secrets → entrypoint → `${VAR}` → OpenClaw。  
**未来：** Nacos 替 secret 文件「供数」，**entrypoint 与变量名契约不变**，OpenClaw 无感迁移。
