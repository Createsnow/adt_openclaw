# 工单会话隔离与资料回收场景

适用对象：核对「单人/多人多会话下，附件不串、状态可查、取消/过期清资料」是否按口径落地的工程师与验收同学。

契约正文见 [../openclaw/OA_WORKFLOW_CONTRACT.md](../openclaw/OA_WORKFLOW_CONTRACT.md) 与已注入的 `AGENTS.md`。Redis key 与 action 见 [OA Workflow Bridge（Redis）接入手册.md](OA%20Workflow%20Bridge（Redis）接入手册.md)。阅读顺序见 [../README.md](../README.md)。

**结论先说：同一人全局一张待确认单。** 会话 A 留下未提交确认单时，会话 B **不能**开新单、**不能**补附件，但 **可以**在 B 里确认或取消；处理完才能在 B 报新问题。不要让员工回到上一会话。插件 24 小时未处理自动清除；本会话确认卡不再提示时限，拦截卡仍提示。Redis 待确认单、附件缓冲、取消/过期回收是插件硬拦；「描述作废、必须重新提问」主要靠提示词。对话历史插件不删。通道 inbound 原件插件不删；宿主机 cron 满 24 小时清 `config/media/inbound` 与 `workspace/media/inbound`，步骤见运维手册 **10.4**。

已提交成功之后立刻再报新问题，插件**允许**（新的 `IT-…`）。ledger 挡的是同一内部工单号再打 OA，不是「这个人刚交过就不能再交」。口径见 OA Redis 手册 **3.3**。

上线须同步 `oa-workflow-bridge-redis` 与 `openclaw/workspace-rules/AGENTS.md` 进 Gateway 后重启。未同步前，现网仍是旧逻辑。

## 1. 口径（验收标准）

### 1.0 同一人跨 OpenClaw 会话（已选定）

员工在企微里看不到 OpenClaw 的 `sessionId`。单聊 `/new`、群聊空闲 30 分钟，都会换会话，但还是同一个人。闸门按**人**，不按会话。

| 会话 A 已有未提交确认单时，在会话 B | 允许？ | 插件行为 |
| --- | --- | --- |
| 开新单 `prepare` | 否 | `ALREADY_PENDING`，`sameSession=false` |
| 给旧单补图 / 改稿 `attach` | 否 | 同上（带或不带 `confirmationId`） |
| 查进度 `status` | 是 | `PERSON_STATUS`（无草稿正文，可有摘要） |
| 确认提交 / 取消 | 是 | 只认原发送人，**不要求回到 A** |
| 确认时并入 B 的新图 | 否 | 只提交 A 已暂存附件 |
| 确认或取消之后在 B 开新单 | 是 | 清原会话 `pending-idx` + `person-pending`；B 未用的新图仍留给新单 |
| 24 小时未确认也未取消 | 到期作废 | 回收 pending / staging / inbox，ledger=`expired`，下一轮必须重新提问 |

员工可见先写拦截卡：`⚠️ **还有一张未提交的确认单**`，上一张抄 `status` / `ALREADY_PENDING` 的 `summary` / `location` / 附件计数（分行，不要斜杠拼接），刚才说的抄本会话这一句。口令写成「确认提交上一张 / 取消上一张」。不要说「请回到上一会话」。拦截卡保留「现在不能给上一张补图或改描述」和 24 小时。本会话确认卡在工单信息与 `---` 之间写补充引导句（无附件「内容不对或还缺信息…」，有附件「还可以继续改文字…」），不要 24 小时，不要写成 `3. 补充`。口径见 `Aidy企微回复模板.md`。取消旧单且本会话已报新问题时，同一轮「🗑️ **上一张已取消**（问题）」+ `---` 接力当前单（差什么复用 3 / 4b / 4c / 4d 短卡，不要一律问园区），不要只回取消短句。

### 1.1 单人多会话

| 编号 | 要求 |
| --- | --- |
| a | 上下文里的文件、图片不要串到另一个 OpenClaw 会话。但可以查**这个人**当前工单状态（未提交 + 已提交） |
| b | 明确取消后，删除该单相关资料（图片、文档、描述）。下一轮必须用户重新提问 |
| c | 用户未确认提交则保留 24 小时；到期删除图片、文档、描述。下一轮必须用户重新提问 |
| d | 会话 A 有未提交单，新会话又提新问题：只能确认或取消，不能补充资料；已补全的文件和图片须在 24 小时内一并提交或取消删除，否则到期全部清除 |
| e | 不要让员工回到会话 A。B 里确认或取消后，即可在 B 报新问题 |

### 1.2 多人多会话

与 1.1 相同：人与人之间工单、附件、状态互不串；每人仍可查自己的未提交 / 已提交。

## 2. 分层：谁在拦什么

| 层 | 管什么 | 硬拦？ |
| --- | --- | --- |
| 插件 Redis | 待确认单、按人状态索引、inbox、ledger | 是 |
| 插件本机 staging | 该单图片/文档副本 | 是 |
| 插件进程内 inbound 缓冲 | hook 到 `prepare` / `attach` 的第一跳 | 是（按「提交人 + `sessionId`」；读取时兼容 hook 只有 `sessionKey` 的单聊） |
| `AGENTS.md` | 取消/过期/`/new` 后不要沿用旧描述旧图 | 否，靠模型执行 |
| OpenClaw 会话 jsonl | 聊天记录里的旧文字、旧 `[media attached]` | 插件不删 |
| 通道 `media/inbound` 原件 | 企微落盘的源文件 | 插件不删，通道自己回收 |

附件隔离键：`提交人 + OpenClaw sessionId`（没有 `sessionId` 时退回 `sessionKey`）。Hook 事件可能只有 `SenderId` / `from.userid` 和 `sessionKey`，工具 ctx 才有 `requesterSenderId` + `sessionId`；`attach` 会按候选键读取同一缓冲，单聊 `sessionKey` 已包含发送人才回退到裸键，群聊不回退。正文见 OA Redis 接入手册 3.6。  
待确认闸门：同一人**全局**一张（`person-pending`），跨 `/new` 仍拦住。  
查状态：`status` 可不传 `confirmationId`，回执 `PERSON_STATUS`。

## 3. 单人多会话

| 场景 | 覆盖 | 实际行为 |
| --- | --- | --- |
| 同一人 `/new` 后，旧图 / 旧文件不进新 `prepare` | 已覆盖 | 附件跟 `sessionId`；尚未 `prepare` 的 Redis inbox 在 `/new` / `session_end` / 换 sessionId 时立刻清掉 |
| 同一人 `/new` 后仍能查待确认 | 已覆盖 | `status` 不带 ID → `PERSON_STATUS.pending`（无草稿正文，含 `summary` / `location` / 附件计数） |
| 同一人 `/new` 后仍能查已提交 OA 单号 | 已覆盖 | `PERSON_STATUS.submittedCount` + 最多 5 条 `submitted[].requestId`（`recent` 仍最多 20 条摘要） |
| 同一人 `/new` 后旧待确认仍拦住新 `prepare` | 已覆盖 | `ALREADY_PENDING`，回执带已有 `confirmationId`、`expiresAt`、`retentionHours`、`sameSession=false` |
| 同一人在新会话里确认或取消旧单 | 已覆盖 | 只认人，不认旧 `sessionId`；确认只提交旧单已暂存附件。成功后清原会话 `pending-idx` 与 `person-pending`，新会话才能再 `prepare`。跨会话确认不清新会话 inbound |
| 同一人在新会话里给旧单补图 / 改稿 | 已覆盖 | `attach`（带或不带 ID）和跨会话确认时的新 inbound 都被拦住；只能确认或取消 |
| 新会话取消后，旧图不灌进新对话 | 已覆盖 | 会话变了就不回灌附件 |
| 新会话取消后，模型不再用旧描述建单 | 半覆盖 | 插件已删 Redis 草稿；对话历史还在。`AGENTS.md` 禁止沿用旧描述、旧图、旧地点 / `systemName` |
| 群聊空闲 30 分钟自动新会话 | 半覆盖 | 若 OpenClaw 换了 `sessionId`，附件隔离生效。单聊默认**不会**自动新会话，见第 7 节 |

## 4. 明确取消

| 场景 | 覆盖 | 实际行为 |
| --- | --- | --- |
| 取消后删 pending / staging / 该单 inbox | 已覆盖 | ledger 记 `cancelled` |
| 同一会话、下一句不再带旧图旧文档 | 已覆盖 | 下一轮 `message_received` 丢掉 cancel 回灌的附件 |
| 同一轮「改稿 = cancel 再 prepare」仍保住附件 | 已覆盖 | 有意保留，避免补一句话把图弄丢 |
| 取消后必须重新说明问题 | 半覆盖 | 插件不再提供旧草稿；对话历史还在。`AGENTS.md` 现禁止沿用上一张单的描述、图片、地点 / `systemName`；电脑类新问题必须重新问 1–6 |
| 通道磁盘上的 inbound 原件 | 插件不删 | 插件从来不删。人多涨盘：运维手册 **10.4** 对 `~/aidy/config/media/inbound` 与 `~/aidy/workspace/media/inbound` 做满 24 小时 cron，不要手删整个 workspace |
| 取消台账 | 留下 | `cancelled` 可点查，不是「此人名下空空」 |

员工可见：没有在途当前单时只回「🗑️ 好的，这张单已取消。」。跨会话取消且本会话已报新问题：同一轮「🗑️ **上一张已取消**」+ `---` + 当前单（差地点问 1–6；差邮箱/文件国内越南、MES B/C、IT 需求字段则复用对应短卡；事实已齐则 `prepare` 出当前确认卡），禁止只回取消短句。

## 5. 未确认满 24 小时

`pendingTtlHours` 默认 24。到期判定看 pending JSON 的 `expiresAt`。

| 场景 | 覆盖 | 实际行为 |
| --- | --- | --- |
| 到期不能再确认提交 | 已覆盖 | `submit_confirmed` → `CONFIRMATION_EXPIRED`，并回收 |
| 到期删 pending / staging / inbox | 已覆盖 | 在 `status` / `prepare` / `attach` / `submit` / `cancel` 时回收；ledger 记 `expired`；staging GC 不再只靠下一次 `prepare` |
| 到期后下一轮 `prepare` 不带旧图 | 已覆盖 | |
| 员工可见 24 小时提示 | 半覆盖 | 本会话确认卡不再写。拦截卡仍保留。回执带 `retentionHours` / `expiresAt`；插件仍按 24 小时回收 |
| 到期后必须重新提问 | 半覆盖 | 同取消：草稿没了，聊天记录还在 |
| 无人再说话、只靠 Redis TTL | 半覆盖 | pending 约 24h+60s 被 Redis 删掉；磁盘 staging 要等下次任意 `oa_workflow` 调用触发 GC |
| 建单前 inbox（只发了文件、还没 `prepare`） | 不是 24h | 默认 **30 分钟**（`inboxTtlMinutes`，对齐 OpenClaw `idleMinutes`）。`/new` / 自动新会话立刻清；过期后要重新发文件 |

`status` 点查过期 pending：先返回 `CONFIRMATION_EXPIRED`，pending 已被回收；再 `cancel` 可能是 `NOT_FOUND`。不要再 `submit_confirmed`，不要沿用旧描述旧图。

## 7. OpenClaw 何时开新会话（配置未改）

现网 `openclaw.json`：

```json
"session": {
  "dmScope": "per-channel-peer",
  "resetByType": {
    "group": {
      "mode": "idle",
      "idleMinutes": 30
    }
  }
}
```

| 会话类型 | 自动开新会话 | 说明 |
| --- | --- | --- |
| 企微单聊（`chattype: single`） | **不会** | 没有 `resetByType.direct`，默认 `mode: none`。只有 `/new`、`/reset`。建单前 inbox 仍 **30 分钟**过期 |
| 企微群聊 | 空闲 **30 分钟** | 无真实用户互动后换 OpenClaw 会话；尚未 prepare 的附件随 `session_end` 立刻清，TTL 也是 30 分钟 |

即便 OpenClaw 开了新会话，插件仍按**人**记住待确认单，所以可以查状态、确认或取消，**不能**补附件或开第二张待确认；附件不会跟着进新对话。员工不必回到上一会话。

## 8. 原有工单主路径（本次未拆，仍有效）

与隔离规则兼容，验收时不要回归：

- 普通建单 → 待确认 → 确认提交 / 取消
- 当场提交（`帮我提交` 等）→ `prepare` 后立刻 `submit_confirmed`
- 待确认中只发图 / 文件 → `attach`（不换 `confirmationId`）
- 同一轮文字改稿 → `cancel` + `prepare`，附件还在
- 企微把正文和附件拆成两条 → inbox / inbound 暂存后再认领
- 身份未映射、桥接未开通、OA 对账中（`unknown` / `RECONCILIATION_REQUIRED`）
- 已提交幂等：同一确认单再提交 → `ALREADY_SUBMITTED`

## 10. 和现网那次日志的对照

路径：`/new` → 碰到旧待确认 → 取消 → 「帮我提交」又带上 2 张旧图。  
另一条：只发了图和文档、还没 `prepare`，再 `/new` 后确认卡仍写「1份图片、1份文档」。

按新逻辑应变成：

1. `/new` 后旧图**不会**进新 `prepare`。尚未 prepare 的 Redis inbox 在 `/new` / `session_end` 立刻清掉；换 `sessionId` 也不会认领。
2. `status`（可不带 ID）仍能看到那张待确认单，并带 24 小时时限。
3. 新会话 `attach` / 再 `prepare` 应 `ALREADY_PENDING`（`sameSession=false`），只能确认或取消。
4. 取消后，插件侧旧图、旧草稿清掉。
5. 再「帮我提交」若没重新说问题：规则要求先重新提问。若模型仍拿聊天记录重开，那是提示词执行问题，不是插件又回灌了附件。

## 11. 验收清单

插件与 `AGENTS.md` 已同步并重启后，建议按人走一遍：

1. 会话 A：发图 + 描述 → `prepare` 待确认。
2. `/new` 进入会话 B：只发「你好」不应带出旧图；问进度：可确认的待确认看出确认/拦截卡；对账中（`unknown`/`submitting`）应看到「OA 需要人工核对」，不要 1 / 2。
3. 会话 B：`prepare` / `attach` 应 `ALREADY_PENDING` 且 `sameSession=false`，且新单附件数为 0。拦截卡含分行的「上一张」和（若本会话已报新问题）「刚才说的」；口令是「确认提交上一张 / 取消上一张」。不含「补充请直接发图片」，但含 24 小时清除提示。不要出现「请回到上一会话」。
4. 会话 B 只打招呼后取消旧单 → 只回「🗑️ 好的，这张单已取消。」；再 `prepare` 不得带旧图；不得沿用旧描述，除非员工重新说了问题。同一会话取消或提交后，再发「电脑坏了」必须重新问 1–6，不得直接确认卡。
4b. 会话 B 已报新问题（如「电脑坏了」，或已选地点）再取消旧单 → 同一轮「🗑️ **上一张已取消**（问题）」+ `---` + 当前工单（差地点则 `📝 已记下：…` 后问园区 1–6；差邮箱/文件国内越南、MES B/C、IT 需求则复用 4b–4d，不要一律问园区；事实已齐则 `prepare` 出当前确认卡并回显问题 / 地点 / 附件）。不得只回取消短句；不得沿用旧单地点 / 描述 / 图片。`/new` 后第一句新问题应先 `status` 出跨会话拦截卡，不要先问地点。
5. 另开一人（或群里另一人）：发自己的图建单，不得出现甲的图或甲的单号。
6. 待确认单用测试手段把 `expiresAt` 打到过去：`status` / 再 `prepare` 不得带旧图；ledger 为 `expired`。
7. 会话 A 待确认后发确认卡，头行 `📋 **当前工单**`，正文含 `💬 问题：` /（有地点则）`📍 地点：` /（有附件则）`📎 附件：`，再写补充引导句（无附件「内容不对或还缺信息，直接再写一句，或发图片、文档。」；有附件「还可以继续改文字，或再发图片、文档。」），然后一条 `---`，再 `**请回复**` + `1. 确认提交` / `2. 取消`。不要缺 `---`，不要把 `**请回复**` 写成「请回复」。不要出现「请确认后提交」、`3. 补充` 或 24 小时。拦截卡仍不含本会话补充引导句。
8. 会话 B：确认提交 → 只带 A 的旧图，不并入 B 的新图；原会话 `pending-idx` 与 `person-pending` 已清；同一人在 B 可再 `prepare`，B 里未用的新图可以进新单。
